# Amazon S3 to Google Cloud Storage (GCS) Migration

## Prerequisites

- IAM permissions to create Storage Transfer Service (STS) jobs and GCS buckets.
- Read access (`s3:GetObject`, `s3:ListBucket`) on source S3 buckets.

## Procedure

### 1. Provision Target GCS Buckets
- Create GCS bucket matching location strategy (regional in the same region as primary GKE cluster, or multi-regional if access patterns are global).
- Set default storage classes and encryption settings.
- Mirror lifecycle rules (`delete` or `transition` to Nearline/Coldline/Archive) to match S3 bucket policies.

### 2. Configure Storage Transfer Service (STS)
- Create a transfer job from source S3 to destination GCS bucket.
- Perform initial full synchronization.
- Enable event-driven continuous sync (using SQS/EventBridge notifications from S3) or scheduled daily/hourly syncs during co-existence.

### 3. Cutover Sequence
1. Freeze final modifications to source S3 bucket if application requires strict cutover boundary.
2. Run final delta transfer via STS.
3. Validate object counts and MD5/CRC32C hash sampling between S3 and GCS.
4. Repoint application environment variables and bucket names to GCS.
5. Keep S3 bucket read-only during the 14-day soak window before retiring the STS job and deleting S3 data.

## Validation

- Total object count and total byte count in GCS matches source S3 bucket (minus lifecycle deletions).
- Random sample of object checksums verified.
- Lifecycle rules confirmed active on GCS (`gcloud storage buckets describe`).

## Common pitfalls

- **S3 ACLs / Signed URLs do not translate**: S3 signed URLs do not work on GCS. Applications must be updated to generate GCS signed URLs (using GCP service account key/workload identity signing) at the application layer (`workload-translation`).
- **Default TCP Buffers & WAN Transfer**: For custom bulk transfer scripts outside STS, ZFS/file send over WAN bottlenecks at default Linux TCP buffers (`[LFF-11]`). Always use Storage Transfer Service for multi-terabyte bucket migrations.
